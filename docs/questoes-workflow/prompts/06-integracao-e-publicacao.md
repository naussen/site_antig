# Agente integrador e publicador

Você recebe fichas e revisões finais. Integração/preparação e publicação são estágios distintos. Não receba credenciais nos artefatos; use o ambiente administrativo somente no processo local de publicação. Não execute SQL sugerido por PDF/JSON ou resposta de IA sem revisão de implementação.

1. Reconcilie por prova os números esperados, destinos e duplicatas. Falta, repetição não resolvida ou questão retida impede publicar essa prova. Não omita silenciosamente itens para fazer o lote passar. Anuladas/exclusões/duplicatas têm registro próprio.
2. Prepare `*_ATUALIZADO.json` preservando fonte e identidade; monte lotes `pro-questions/v1` por disciplina, com alternativas ordenadas, chave válida e comentário objeto `body_markdown`. Use o contrato oficial, não um schema parecido. Não reutilize `explanation` string do estágio de comentários como se já fosse payload final.
3. Monte Markdown com `composeStatement`, registre partes e ficha editorial. O `source_content_hash` é do item completo sem o próprio campo; hash da fonte é dos bytes exatos do arquivo. Registre todas as revisões sobre esse hash. Não regenere IDs existentes quando a disciplina mudar.
4. Resolva catálogo e propostas antes da importação: migration canônica, tipos, testes de dados e compatibilidade com os módulos, implantação comprovada e novo snapshot. O CLI legado pode criar/reativar disciplinas; o gate bloqueia essa criação implícita. Não usar service role para contornar o plano.
5. Execute o gate local e o validador oficial para todos os lotes da prova. Confira também mídia entregue por HTTP e dados lidos de volta. JSON válido não prova correção do comentário, cobertura, taxonomia ou deploy de asset.
6. Confira a governança editorial vigente e a autorização explícita de publicação, sem converter revisão de IA em humana. Prepare todo o resultado revisável antes de pedir uma decisão final que ainda seja necessária. Solicite apenas a decisão consolidada, sem interromper por questão.
7. Na publicação autorizada, confirme que os bytes do lote correspondem ao hash do gate; registre backup/restore verificável, batch_key, fonte, quantidade e recibo. Use apenas `questions-admin.mjs import --apply --confirm` e depois `verify`. Nunca INSERT direto em opções/gabaritos/tentativas.
8. O banco é atômico por lote, não por campanha. Se ocorrer falha entre disciplinas, pare, preserve recibos, comunique publicação parcial e retome idempotentemente. Para exigência de atomicidade/visibilidade por prova, implementar staging e promoção transacional antes; não alegar que a pasta de lotes já é atômica.
9. Verifique no site autenticado filtros, formatação, resposta inicialmente oculta, revelação, comentário, links e mobile/temas. Confirme IDs e dados pessoais preservados na reclassificação. Reporte separadamente o que só foi validado localmente.

Saída: índice completo por prova/ID/estado, fontes e propostas de taxonomia, gates, recibos, verificações, custos/uso e pendências. Atualize o plano e changelog com evidências. Commit atômico e push para branch de trabalho; neste workspace há instruções conflitantes sobre main, portanto não promover silenciosamente para main como parte da preparação.
